# Codex subscription integration investigation

Task: `TreeTutor-7t3.1`. Reviewed: 2026-11-07 (America/Edmonton).

Status: documentation investigation complete; runtime integration unverified. This note proposes checks, not an implementation decision. No app-server, authentication flow, or model request was started. The task and PRD authorize requirements research only.

## Conclusion

Codex app-server is a documented interface for embedding authentication, conversation history, approvals, and streamed agent events in another product. Its managed ChatGPT login provides a subscription-backed candidate. However, the current auth section explicitly permits continued use by existing local/open-source apps, recommends Sign in with ChatGPT (SIWC), and excludes commercial/hosted services. This does not establish blanket eligibility for a new TreeTutor integration. [App-server introduction and authentication](https://learn.chatgpt.com/docs/app-server#auth-endpoints)

Current SIWC documentation offers a clearer new-client candidate: OAuth-authorized ChatGPT plan usage for open-source and locally hosted apps, including a documented Codex app-server configuration. First registration uses a dynamic client flow without a client secret or partner API key. Account/workspace eligibility and granted plan-use scopes still require verification. Paid/remotely hosted apps follow a separate interest process. [Plan usage overview](https://developers.openai.com/siwc/token-sharing-open-source), [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)

Recommendation for the later architecture decision: evaluate SIWC-backed app-server first, preserving the managed-login findings as an alternative requiring eligibility clarification. This remains subscription access through the official OpenAI endpoint, not API-key billing or a generic custom-endpoint feature. It does make TreeTutor responsible for OAuth credential storage and renewal; that choice is not adopted by this research task. [SIWC app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

## Documented capabilities and limits

| Requirement | Documentation evidence | What remains unverified |
| --- | --- | --- |
| Subscription authentication | Managed `account/login/start` supports `chatgpt` and `chatgptDeviceCode`; Codex owns token persistence/refresh. `account/read` and `account/updated` expose account/auth mode. ChatGPT sign-in uses subscription access; API-key sign-in uses separately billed access. [Auth modes](https://learn.chatgpt.com/docs/app-server#authentication-modes), [authentication](https://learn.chatgpt.com/docs/auth#openai-authentication) | New-app eligibility for the legacy managed-login route, user/workspace permissions, actual login success. |
| SIWC subscription candidate | App obtains consent and OAuth access token, passes it only to the app-server child environment, and configures the official Responses provider. No separate Codex login is needed. App refreshes token and restarts app-server, then resumes saved thread IDs. [SIWC app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) | Consent/admission, selected account's plan access, local CLI compatibility, refresh during concurrent work. |
| Streaming | `initialize` → `initialized`, then `thread/start` and `turn/start`; `item/agentMessage/delta` streams text. Final `item/completed` is authoritative; only `turn/completed` with status `completed` means success. `failed` and `interrupted` are separate outcomes. [Lifecycle](https://learn.chatgpt.com/docs/app-server#lifecycle-overview), [events](https://learn.chatgpt.com/docs/app-server#events) | Exact event envelopes in installed schemas, interleaving and terminal-event handling. Route by verified thread/turn/item identifiers, never whichever box is focused. |
| Model selection | `model/list` returns model/effort choices; `thread/start` and `turn/start` accept a model; resume with another model emits a warning and a model-switch instruction. [Models](https://learn.chatgpt.com/docs/app-server#models), [threads](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread) | Access to each selected model. On SIWC provider configuration, RPC `model/list` may be a bundled catalog, not an entitlement check. Account-specific `/v1/models` is documented; completed inference verifies access for that request. [SIWC models](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) |
| Persistence/resume | Save `thread.id`; call `thread/resume` and retrieve stored turns/items through pagination. SIWC's `store: false` does not disable local thread history/resume. [Threads](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread), [SIWC limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) | Resume after a fresh process, model changes, token renewal; app-level persistence is still required for tree structure, canonical messages and branch snapshots. |
| Concurrent conversations | Thread IDs identify conversations; turns target a thread; APIs list loaded threads and subscribe to events per thread. Forks can share a root `sessionId`, so `sessionId` alone cannot identify a canvas conversation. [Threads](https://learn.chatgpt.com/docs/app-server#threads) | Two independent generations overlapping on one process/account; shared quota/serialization limits; no cross-thread leakage. Multiple loaded threads alone is not proof of parallel inference. |
| Supplied history | `thread/inject_items` appends prebuilt Responses items to a loaded thread without starting a turn, persists them and includes them in later model requests. Its example injects an assistant message. The section does not label this method experimental; check the installed schema before relying on that. [Inject items](https://learn.chatgpt.com/docs/app-server#inject-items-into-a-thread) | Installed support; valid user/assistant/developer item shapes, ordering, exposure through history reads, persistence on resume and semantic continuity. |
| Cross-provider continuity | A provider mismatch during resume/input returns `modelProviderMismatch`; docs suggest reading stored history or forking with the current configured provider. [Resume](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread) | This does not prove Claude subscription integration or a bidirectional history conversion. TreeTutor needs a canonical transcript and fixed inherited snapshot independent of provider-specific thread IDs. |
| Cancellation/errors | `turn/interrupt` targets thread and turn, then the turn finishes interrupted. Errors include unauthorized, usage limits and context exhaustion; `willRetry` distinguishes active retry from terminal failure. [Interrupt](https://learn.chatgpt.com/docs/app-server#interrupt-a-turn), [errors](https://learn.chatgpt.com/docs/app-server#errors) | Cancellation isolation, partial-text handling, auth recovery without losing saved history. |

SIWC requires HTTP inference to stream with `store: false`; required history travels in input rather than persistent remote conversation state. Explicit system-role messages are rejected; use instructions/developer messages. App-server takes its own RPC inputs, not arbitrary Responses parameters. These constraints must inform any history adapter. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

## Smallest later prototype

One command-line harness, one installed `codex app-server` child using stdio, two persistent root threads, one fresh branch thread, and synthetic text fixtures. No frontend, canvas, database, Claude execution, or general provider abstraction is needed for this check. Generate schemas from the installed CLI and pin/report its version before choosing RPC fields; generated schemas are version-specific. [Protocol and schemas](https://learn.chatgpt.com/docs/app-server#message-schema)

Keep a mapping from logical conversation ID to provider thread ID and from active turn/item IDs to their conversation. Save synthetic transcripts and fixed branch context separately from provider metadata. Capture timestamps and redacted protocol events so isolation/concurrency claims can be checked without relying only on model answers. This is a proposed harness design, not a claim about implemented storage.

Use a disposable working directory and explicit restrictive tool/read permissions; handle approval requests by declining unrelated actions. Read-only sandbox defaults can still allow broad reads. Do not expose process execution or `thread/shellCommand` to tutoring: these documented operations can run outside the thread sandbox. Isolate configured MCP/plugins/hooks/instruction sources before testing; merely asking the model not to use tools does not enforce isolation. [Sandbox read access](https://learn.chatgpt.com/docs/app-server#sandbox-read-access-readonlyaccess), [approvals](https://learn.chatgpt.com/docs/app-server#approvals), [thread shell command](https://learn.chatgpt.com/docs/app-server#run-a-thread-shell-command), [process execution](https://learn.chatgpt.com/docs/app-server#process-execution)

Prefer stdio between backend and child; no direct browser app-server connection is needed. The app-server page labels TCP WebSocket transport experimental/unsupported. TreeTutor's future HTTP server must bind loopback per PRD. [Protocol](https://learn.chatgpt.com/docs/app-server#protocol)

## Pass/fail checks for the authorized prototype

All checks below remain **NOT RUN**. Record CLI version, auth route, model, timestamps, terminal status and redacted evidence for every run. Treat a timeout, missing terminal event or untested prerequisite as unverified, not a pass.

| Check | Procedure | Pass condition |
| --- | --- | --- |
| Protocol compatibility | Generate installed JSON schemas; inspect start/resume/injection/event fields and capability gates. | Required fields and history items are supported; record any experimental opt-in. Stop on incompatibility rather than invent fields. |
| Subscription auth | After route selection and authorization, use managed ChatGPT login or SIWC plan-use consent; check account/permissions through that route. Complete one synthetic turn. | Correct account and subscription route; completed inference without API-key substitution. No credentials in frontend, transcripts or logs. |
| Stream assembly | Ask for several paragraphs, record deltas and completed items. | Incremental text arrives before completion and final displayed content matches authoritative completed message, without duplication. |
| Two simultaneous isolated sessions | Start A with unique private fact A and B with unrelated fact B. Start B before A terminates; log both lifecycles. Ask each to recall its own fact and later probe the other's. | Both active intervals overlap, each produces text before the other terminates, each completes, no event reaches the wrong conversation, each recalls its own fact. Negative probes alone do not prove isolation: inspect submitted histories too. |
| Resume across restart | Save A/B IDs and messages, stop harness/server, start fresh and resume both; ask about earlier facts. | Both histories retained and correctly associated; new turns complete with correct recall and no duplicated user messages. |
| Supplied role history | Create fresh C. Inject synthetic user/assistant exchange with a fact supplied only in the assistant message; add fixed developer/inherited context using schema-supported shape. Send a follow-up, restart/resume, repeat. | Model uses imported facts/roles in correct order before and after restart; persisted evidence confirms context remains. Unsupported item shapes or lost context fail this route. |
| Fixed child context | Create child with compact ancestor snapshot + exact selected passage + question. Continue parent with a new secret and child with a different secret; continue both. | Child uses fixed initial snapshot; submitted child history lacks later parent secret; parent history lacks child secret; source transcripts remain unchanged. Full-history `thread/fork` alone does not satisfy compact-context requirement. |
| Model change | Select a second available model, send follow-up on the same conversation, then reopen/resume. | Requested model honored or explicit rerouting reported; facts/history persist. If only one model is available, record blocked/unverified. |
| Cancel A while B runs | Interrupt A by its thread+turn IDs. | A ends interrupted with partial text marked accordingly; B continues and completes; subsequent A turn still works. |
| Auth/limit failure | Use isolated test credentials or fixtures for revoked/expired auth, declined consent and quota exhaustion; do not log out or revoke shared user credentials. | Explicit recoverable failure, retained history/partial status, no infinite retry/login loop, no silent API-key fallback. Fixtures verify handler logic only; label real-provider recovery separately. |
| SIWC token renewal, if selected | Refresh through documented OAuth flow, restart child, initialize and resume saved threads; account for active turns before restart. | New token works; no lost/duplicated messages or falsely completed active turns. Correct resumed histories on both conversations. |

Use bounded synthetic fixtures; do not deliberately exhaust quota. Keep full cross-provider switching in `TreeTutor-7t3.4` and Claude eligibility in `TreeTutor-7t3.2`; success here cannot certify them.

## Local evidence and authorization boundary

Read-only main-agent checks found `codex-cli 0.167.0` and an available `codex app-server --help` entry with stdio default plus `generate-ts`/`generate-json-schema` commands. Local help marks app-server experimental. This proves executable availability only; schemas were not generated and runtime behavior was not tested. Published documentation may describe fields absent from that installation.

Before the later prototype, obtain explicit authorization to write/run its harness, start app-server, perform authentication/consent and send synthetic prompts using subscription quota. Choose managed login only after clarifying new-app eligibility, or select the documented SIWC route and its app-owned OAuth responsibilities. Do not inspect/copy existing credential files or change the user's shared login as part of this spike. Official auth docs describe shared credential caching and the sensitivity of cached tokens. [Credential storage](https://learn.chatgpt.com/docs/auth#credential-storage)

Remaining uncertainty: actual account admission, installed protocol support, real overlapping inference, imported-history persistence and semantic quality, secure text-only configuration, refresh interruption behavior, and Claude interoperability. Documentation support is sufficient to design the next check, not to declare the initial text release feasible or tested.
