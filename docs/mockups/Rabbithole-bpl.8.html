Board polish: the tutor writes a code block on the board line by line

Rabbithole-bpl.8. The tutor writes code on the board: a code op opens a panel, and each line op adds one line, highlighted in the theme's colours, as the tutor talks about it. Each line is a board item the spotlight, the pointer, the pen and erase can reach. Spec: docs/board-polish-spec.md (Code block component). The spec wins where they differ.

  • Sizes are board units on the fixed 1600×900 board. Text, arrows, pointer, pen and spotlight are Rabbithole-bsk.3 and bsk.6's.
  • The code panel is the code op's box: the raised surface colour (popover), 16 radius, no border. Lines sit 40 in from its left, the first baseline 36 + 0.8 × size below its top, rows 1.5 × size apart (45 at 30).
  • Lines are the board's monospace font, 30 units at full size, top-aligned. Leading spaces are kept as typed; tabs are not expected.
  • The block shrinks as one to fit its box, down to a 20-unit minimum. Past that, a too-long line clips with an ellipsis and a row below the box is skipped and logged.
  • Highlighting: Prism tokens map to the theme's syntax roles exactly as chat code fences do (src/markdown/codeTokens.ts). Comments are italic. The mockup shows roles in family hues; the app uses astryx-token-<role>. No colour is fixed.
  • A line draws in left to right at about a component child's length (draw-first, Rabbithole-bpl.3). The panel appears with the code op.
  • Spotlight: a line is lit on its own; the block's other lines dim to 30% like any other item. The panel never dims.
  • The prompt asks for about 12 lines per block and a new page beyond that; the app does not enforce it. Not in scope: running code, line numbers, copying code out.
  • Captions show the sentence being spoken. Frames read left to right, top to bottom. Dashed boxes are mockup markers only.

2. Line by line

Each line op adds one row under the last, in order, top-aligned in the panel. A line draws in left to right like a text label, with the board's pen sound. The spotlight is off in these frames so every row reads.

Op names and arguments are the spec's; the op parser owns their exact syntax.

3. Highlighted in the theme

Prism tokenizes each line the way chat code fences do, and every token takes the theme's syntax role colour (astryx-token-<role>). The mockup shows the roles in the family hues; switch to Light at the top to see the same roles in the light scheme.

keyword: def if return function: factorial type: print number: 1 5 string: "cart" comment: # 120 operator, punctuation: * ( ) : plain: n

4. Reaching one line

Every line is a board item with its own id, so the spotlight, the pointer, the pen and erase each reach a single line.

5. Long lines shrink, then clip

The layout fits the block to its box. The whole block shrinks as one, from 30 down to a 20-unit minimum, so a long line shrinks every line with it. Past the minimum a too-long line clips with an ellipsis and a row that would fall below the box is left out. Nothing ever draws outside the panel.

6. Unknown language and bad lines

An unknown or missing lang renders plain. A malformed line, a line whose parent is not a code block, or a bad parameter on code is skipped and logged, with no notice on the board. A code box that overlaps another item or leaves the board follows the same rules as every other component.

l3 line "    if n <= 1: in cb      ← skipped, logged: unterminated string
